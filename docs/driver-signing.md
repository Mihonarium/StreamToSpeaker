# Driver signing & release pipeline

How Stream To Speaker gets from "commit on main" to a release users can
install on stock Windows 10/11 — Secure Boot on, no test-signing mode —
using the central EV-signing repo (`Mihonarium/signing`) plus Microsoft
**attestation signing**.

## Why attestation signing

Windows 10+ only loads kernel drivers signed by Microsoft. There are two
Partner Center routes:

- **Attestation signing** — no HLK testing; Microsoft signs the `.sys` and
  the catalog with the *Microsoft Windows Hardware Compatibility Publisher*
  certificate. The result loads on Windows 10 1809+ / Windows 11 desktop,
  **including with Secure Boot enabled**. Limits: it cannot be published to
  Windows Update for retail audiences (we distribute via GitHub releases, so
  that's fine), it does **not** load on Windows Server ≥ 2016, and Microsoft
  frames it as "not Windows Certified" (no compatibility assurances). This
  is what our pipeline automates.
- **WHQL / HLK** — full hardware-lab testing (the HLK playlist on a lab
  client, an `.hlkx` package signed with the EV cert, submitted by hand),
  Microsoft's blessed retail path and the one the Microsoft Store expects
  (policy 10.2.4). **This is what ships since driver 1.1.0.209** — see
  Flow D. The lab run itself is not automated; everything after
  Microsoft returns the signed package is (`driver-certified.yml`).
  Certification is **per binary**: any change under `driver/` or
  `include/` needs a new HLK run before installers can bundle a
  certified driver again (they fall back to attestation, then to
  test-signed).

Facts the pipeline design leans on (from the attestation docs, verified
2026-08): the submission is a **CAB** containing the driver package in a
subdirectory (no files at CAB root) — `.inf`, `.sys`, and `.pdb` (required
for Microsoft's crash-analysis tools); catalog files are regenerated by the
dashboard, so ours is optional; the **CAB itself must be EV-signed**, but
the binaries inside don't need our signature (Microsoft overwrites embedded
publisher signatures anyway); the returned zip keeps the same directory
layout, with the INF **byte-identical**, a Microsoft-signed `.cat` added,
and the `.sys` embed-signed.

## The pipeline

```
driver/​** or include/​** change on main
        │
        ▼
[driver-submission.yml]  auto (main only)
  build unsigned driver → submission CAB → driver-v<ver> prerelease
  → EV-sign CAB via Mihonarium/signing   ← human: 1 approval click
        │
        ▼
[driver-attest.yml]  run it with tag=driver-v<ver> (by itself only
                     when the repository variable AUTO_ATTEST is true)
  create Partner Center product+submission via the Hardware API
  → upload EV-signed CAB → commit → poll (~10 min typical)
  → attach returned StreamToSpeaker-Driver-<ver>-Microsoft.zip
        │
        ▼
[driver-attested.yml]  auto (called by driver-attest; manual = fallback)
  verify Microsoft signatures + INF identity → canonical
  StreamToSpeaker-Driver-<ver>-Signed.zip → manifest attested=true
        │
        ├──────────────────────────────────────────────┐
        ▼                                              ▼
[build.yml, every main push]                 [build.yml, tag v* push]
  extra artifact: installer bundling           sign-service → package →
  the attested driver (when its                verify-driver → sign-release
  source_hash matches HEAD's driver            → publish: draft release with
  source — service-only commits keep           attested driver + EV-signed
  matching)                                    service exe + EV-signed
                                               setup exe, published when
                                               complete
                                               ← human: 2 approval clicks
```

The pairing rule everywhere: a driver-v release records
`source_hash = hashFiles('driver/**', 'include/**')` at submission time,
and installer builds only bundle a Microsoft-signed driver whose
`source_hash` equals the driver-source hash of the commit being built.
Driver changed since the last signing round → installers fall back
(preview: skipped; release: `-testsigned` suffix + warning, published as a
pre-release that is never the latest release) until you run the loop
again.

**Selection order** (`.github/scripts/Get-AttestedDriver.ps1`, used by
`build.yml` previews and the tagged `package` job): among matching
releases, a manifest with `certified: true` (WHQL, Flow D) always beats
`attested: true` — even with a lower `driver_build` — and within one kind
the highest build wins. The artifact/summary names the kind
(`-certified` / `-attested`). Two guards keep the attestation machinery
from overriding a certified driver: `Driver submission` starts with a
`certified-guard` job that exits (green, with a notice) when a certified
release already matches the current source hash (dispatch with
`force=true` to override), and `Driver attest`'s automatic hand-off is
**opt-in** via the repository variable `AUTO_ATTEST=true` (otherwise the
`workflow_run` trigger only logs why it did nothing; manual dispatch
always runs).

`hashFiles()` is checkout-dependent: on the windows-2022 runners it sees
CRLF-converted text files (`core.autocrlf=true`) in NTFS directory order.
`python3 .github/scripts/certified.py hash` reproduces that value from a
Linux checkout (validated against the `driver-v1.1.0.204` manifest), so
you can predict whether a branch will pair with a release before pushing.
Anything that computes the hash for a manifest must run on windows-2022,
like `build.yml` does.

## How the chain writes driver releases

A `driver-v*` release is the record of one driver binary, and the release
of a driver Microsoft certified or attested can't be made again.

**Start these workflows from main only.** `Driver submission`, `Driver
attest`, `Driver attested` and `Driver certified` run the workflow file of
the ref you pick under "Use workflow from". Branches and tags that exist
today (older `v*` tags, older branches) carry earlier versions of these
files, whose jobs can overwrite a release, a finished one included, when
someone with write access starts them there. Before you click "Run
workflow", check that "Use workflow from" says `main`. A re-run uses the
workflow files of the commit the run was started on: re-run only runs
started from `main`, and for a run from before this version of the
workflows start a new run instead. To try a change to these workflows,
use a dry run from the branch of that change only.

Every job of these workflows that writes a driver release does it through
`.github/scripts/driver_release.py` (tests: `test_driver_release.py`):

1. A **finished** release (manifest `certified: true` or `attested: true`)
   is never changed: nothing is uploaded to it, replaced on it or deleted
   from it, and its notes stay. Running a step again that would write the
   bytes it already holds succeeds and changes nothing; anything else is
   refused with the release named.
2. Each workflow writes only what is its to advance. `Driver submission`:
   a new release, or its own commit's build that nobody has EV-signed yet.
   Its `record-signed`: the release that records exactly the CAB it had
   signed. `Driver attest`: an unfinished attestation round. `Driver
   attested`: a round Microsoft returned. `Driver certified`: a release
   prepared by hand for an HLK return. The jobs that write run on `main`
   only and never in a dry run, and every job that can run from a branch
   or in a dry run holds a read-only token and no secret (the jobs that
   hold the signing or Partner Center secrets, `sign-cab` and Driver
   certified's `download`, run on main only).
3. A file the manifest records (with its SHA-256) is never replaced.
4. Nothing is deleted before its replacement is completely uploaded. A
   replacement goes up as `<name>.pending`; then the old asset is deleted
   and the new one renamed. A file already there with the same bytes is
   not uploaded again. A run that stops half way leaves `<name>.pending`
   (with or without `<name>`). Before its first write, a job finishes
   such a file only as its own stopped write:
   - `manifest.json.pending` is put in place only when it is, byte for
     byte, the manifest that job writes next, and only after everything
     the job does before it writes its manifest. (Driver attest can't
     know the ids Partner Center gave it, so there any two ids pass. When
     `manifest.json` is already deleted, the job works out from the
     pending manifest what it would have written over, and can't compare
     what only the deleted one held.)
   - A pending copy of a file the job uploads is never put in place: the
     job deletes it and uploads the file itself.
   - A pending copy of a file the manifest records is put in place only
     in exactly the recorded bytes.

   At any other pending file the job stops and changes nothing (see
   Troubleshooting). Nothing is renamed over a finished `manifest.json`.
5. `manifest.json` is written last, in a call of its own, and only when
   every file it records is on the release.

**Two jobs at once.** Every job that writes a driver release waits in one
repository-wide concurrency group, `driver-release-writes` (no job in it
is cancelled for another: up to 100 can wait), so no two of them write at
the same time, and no job in it waits for a person. On top of that, each
write is decided on the release as it is at that moment: just before it,
the job reads the release again and stops when the release is finished,
when the tag names another release, or when its files changed since the
job read or wrote them. GitHub has no lock on release files, so a person
in the web UI, or a run of an older version of these workflows (see
above), can still change a release in the moment between that read and
the write: one API call, well under a second. If that happens, the
release shows it in one of two ways. Either it holds `<name>.pending` and
no `<name>` (see Troubleshooting), or a release that had just been
finished got the other job's `manifest.json`. In the second case, the run
that finished it shows the manifest it wrote in its summary, under
"manifest.json written to `driver-v<ver>`"; put that one back. Save it as
a file named `manifest.json.pending`, upload it
(`gh release upload driver-v<ver> manifest.json.pending`), delete
`manifest.json` and rename the pending one, with the commands and the
last check under "Clearing a `.pending` asset by hand" (Troubleshooting).

**Readers.** A `manifest.json.pending` is never read as the release's
manifest. The installers' driver lookup (`Get-AttestedDriver.ps1`), the
certified guard and the fallback check stop with an error at a release
that holds `manifest.json.pending` and no `manifest.json` (a manifest
write that stopped half way): they can't rule it out, and a tag's
`package` job fails instead of falling back to the test-signed driver.
Re-running the job that was writing the release finishes the write.
Release lists are always read with every page. The `v*` drafts of the tag
pipeline are written with rule 4 too (`release_draft.py upload`).

## Driver build numbers

The driver's build number (the fourth DriverVer field, and `build=N` in
the service log) defaults to `git rev-list --count HEAD`. That count
restarted when the public history did, so it no longer rises above every
released build: public `main` counted 131 commits in November 2026, below
the **1.1.1.211** of the certified driver (built with an explicit
`DriverBuildNumber=211`), and a branch with more commits can land on a
released number.

`Driver submission` therefore refuses a build whose version is not above
every `driver-v*` release, or whose build number another release already
carries, before it builds anything (`driver_release.py submission-check`).
When the commit count is not above every release's build number, a
driver change needs a dispatch of `Driver submission` from `main` with
`driver_build` above it (above 211 today). The test-signed dev and PR
builds in `build.yml` stamp the commit count too, so their `build=N` can
equal that of a released driver: tell them apart by the signer, not by
the number.

## One-time setup

1. **Partner Center**: register for the [Hardware Developer Program]
   (https://partner.microsoft.com/dashboard/hardware) and associate the
   Certum EV certificate with the account (the EV cert is both the
   registration credential and what must sign submission CABs).
2. **Signing repo**: set up per its README, including the `FETCH_TOKEN`
   environment secret (fine-grained PAT scoped to this repo, Actions:
   Read-only). Unsigned bytes travel to the signing workflow as Actions
   artifacts (its private-source mode) — `FETCH_TOKEN` is how it fetches
   them, after your approval.
3. **This repo — environment `request-signing`** (already exists for the
   installer signing): holds secret `SIGNING_REPO_TOKEN` (fine-grained PAT,
   scoped to only the signing repo, Actions Read+Write). **Add branch
   `main` to its "Deployment branches and tags" policy** (previously tags
   `v*` only) — `driver-submission.yml`'s `sign-cab` job runs from main.
   No required reviewers here; the human gate lives in the signing repo.
4. **This repo — environment `partner-center`** holding the Hardware API
   secrets. Its "Deployment branches and tags" policy is Selected with the
   single branch `main` and no tags, so a workflow edited on any other
   branch or tag can't read them (a repository secret would be readable by
   any workflow run in this repo; keep no repository-level copies). No
   required reviewers, by design — the EV-signing approval already vouches
   for the exact CAB bytes, and the Entra app can only submit to our own
   Partner Center account. Only `Driver attest`'s `reconcile` job and
   `Driver certified`'s `download` job run in it:
   - `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET` — a
     Microsoft Entra app registration associated with the Partner Center
     account (Partner Center → Account settings → User management →
     Microsoft Entra applications, **Manager** role). The reply URL is
     never used (client-credentials flow) — `https://localhost` is fine.
   - Client secrets **expire** (max 24 months). The failure mode is
     `invalid_client` from the token endpoint in `Driver attest` — create
     a new secret in Entra (Certificates & secrets), update the
     environment's `AZURE_CLIENT_SECRET`, delete the old one.
5. **This repo — tag ruleset on `v*`**: creating, moving and deleting `v*`
   tags is restricted, with only the Repository admin role allowed to
   bypass. A `v*` tag starts the installer release chain, and the
   `request-signing` environment's policy limits refs, not people: without
   the ruleset anyone who can push could tag a commit with an edited
   workflow and have it reach the signing requests. The `driver-v*` tags
   CI creates don't match `v*`.

## Flow A — driver changed (2 manual steps)

1. Push/merge the driver change to main (or dispatch `Driver submission`
   from main with `driver_build`, see "Driver build numbers"). `Driver
   submission` checks that it may write `driver-v<ver>` (new, or this
   commit's own unsigned build) and that the version is above every driver
   release, builds the driver **unsigned** (`SignMode=Off`), packs
   `StreamToSpeaker-Driver-<ver>-Submission.cab`, creates prerelease
   `driver-v<ver>` (job `record`) with a `manifest.json` that records how
   the binary was built (`driver_build`, `build_root` = the runner checkout
   it was linked in, `driver_h_stamped`, which the reproducibility check
   repeats) and the unsigned CAB's SHA-256, and dispatches the CAB (the
   run's `submission-cab` artifact) to the signing repo (job `sign-cab`).
2. **Approve** the signing run in `Mihonarium/signing` (its run name must
   show the sha256 from the workflow summary / release notes). The job
   `record-signed` then adds the EV-signed CAB to the release and records
   its hash. If you don't approve within 2 h the `sign-cab` job times out:
   approve, then re-run the failed jobs; `sign-cab` picks up that signing
   run (or reuses its signed file) instead of asking again. If
   `record-signed` failed, re-run it alone: the signed CAB waits as the
   run's `signed-cab` artifact for three days.
3. **Run `Driver attest`** from main with `tag` = `driver-v<ver>` (the
   release notes and the run summary name the tag). It starts by itself
   when `Driver submission` completes on main only if the repository
   variable `AUTO_ATTEST` is `true` (off by default, see "Selection
   order"); then it takes the attestation round of the commit that run
   built. (A `Driver submission` run on any other branch also starts
   main's `Driver attest`, which ignores it.) It
   reconciles the release's `manifest.json` forward: create a Partner
   Center product (`StreamToSpeaker-Driver-<ver>`) + initial submission via
   the Hardware API, record `ms_product_id` / `ms_submission_id` on the
   manifest **before** uploading (so a re-run resumes the same submission:
   a manifest a stopped run left as `manifest.json.pending` is finished
   first, never dropped),
   upload the EV-signed CAB (re-hashed against the manifest first), commit,
   poll (attestation typically completes in ~10 minutes), attach the
   returned `StreamToSpeaker-Driver-<ver>-Microsoft.zip`, then call
   `Driver attested`, which verifies:
   - `signtool verify /kp` against the catalog AND the embedded `.sys`
     signature; signer must be the *Microsoft Windows Hardware
     Compatibility Publisher*;
   - the returned INF is byte-identical to the submitted one, and carries
     the release's DriverVer;
   - the EV-signed CAB on the release is the one whose SHA-256 the
     manifest records;
   then attests the provenance of `StreamToSpeaker-Driver-<ver>-Signed.zip`,
   publishes it, and last flips the manifest to `attested: true`.

**If `Driver attest` goes red, re-run it** (Actions tab → Run workflow;
optional `tag` input, defaults to the newest unfinished attestation round
by creation date, never to a certified or attested release). It is a
reconciler: every step re-reads `ms_state` from the manifest and resumes
exactly where it stopped — a timeout mid-poll, a transient API error, or a
runner death never needs cleanup. Outcomes it can report:

| Outcome | Meaning | What to do |
| --- | --- | --- |
| `wait-signing` | EV-signed CAB not on the release yet | Approve the signing run, let `sign-cab` finish, then run this again |
| `done` | The release is already attested or certified | Nothing; check the `tag` if you expected a new submission |
| `poll-timeout` | Microsoft still processing after ~45 min | Re-run later; state stays `committed` and polling resumes |
| `failed` | Microsoft rejected the submission | Read Microsoft's error payload in the run summary; fix, push a new driver build |

Notes: rapid successive driver pushes to main cancel in-flight submission
runs on main. The newest run's `record` job deletes an older driver
release only when it can show the release is an unsigned build of main
that nothing was ever done with: its only file is a completely uploaded
`manifest.json`, which records nothing but an unsigned build (no
signature, no submission, no package, no field the cleanup doesn't know),
and the commit it was built from is its target and in main's history.
Every other older release is kept and named in the run summary with the
reason; a release that can't be read is kept. A cancelled `sign-cab` can
leave a signing-repo run Waiting — reject it there; its digest no longer
matches anything CI will publish. A `Driver attest` run that stops
between creating the Partner Center product and recording it on the
release can leave an empty product in Partner Center; that's harmless
(products can't be deleted via the API).

A job that waits in `driver-release-writes` (for example Driver attested
while Driver attest polls Microsoft, up to 55 minutes) starts when the job
ahead of it is done; the group cancels nothing waiting there unless 100
jobs already wait. A newer driver push to main does cancel the older
Driver submission run as a whole (its own run-level group), with its
`record` or `record-signed` job, waiting or running; the newer run's own
`record` then writes its release. A job cancelled in the middle of a
write can leave a `<name>.pending` file on the older run's release; it
stays there until that job is run again (see Troubleshooting, "A release
shows an asset named `<name>.pending`"). Don't attach a Microsoft zip by
hand (the manual fallback) while `Driver attest` runs for the same
release: its next write would find the release changed and stop.

## Flow B — every main push (no manual steps)

`build.yml` always produces the dev artifact (test-signed driver + test
cert). If a Microsoft-signed driver matches HEAD's driver source, it
additionally builds `StreamToSpeakerSetup-<ver>-certified.exe` (or
`-attested.exe` when only an attestation-signed one matches: the suffix
names the kind) with that driver package and **no** test cert — the .iss
skips cert import when no `.cer` is staged — as a workflow artifact. Service-only commits keep matching, which is the
point: driver attestation is per driver-source state, not per commit.

## Flow C — tagged release (2 approval clicks)

Tag `vX.Y.Z` → `build.yml` runs the release chain. The version is
assembled in a **draft** release and becomes public only in the last
job: a draft is visible only to accounts with push access, not to
`releases/latest` (the app's update check), the
`/releases/latest/download/` links or the public release list. The
unsigned installer is never a release asset. Runs for the same tag never
overlap (a concurrency group per tag).

1. `build` — normal CI build; exports the service exe + driver-cache
   (test-signed fallback + devcon) to the release jobs. The tag is the
   version (`release_draft.py version`): `<major>.<minor>.<patch>` with an
   optional `-<pre-release>` part only (letters, digits, dots, hyphens; no
   `+` and nothing naming `testsigned`). The crate version is stamped from
   the tag and `cargo update --workspace` updates only the crate's own lock
   entry, so the service is built `--locked` from the commit's
   dependencies. Inno Setup is the pinned `INNO_SETUP_VERSION`, checked by
   the version its compiler engine prints when it compiles
   (`inno_setup.py check`; `ISCC.exe`'s version resource reads 0.0.0 on
   the hosted images, and choco can leave another version in place).
   `chain-tests` and `chain-tests-powershell` (every test in
   `.github/scripts`, the Pester tests among them) run next to it; the
   release jobs wait for them.
2. `sign-service` — creates the **draft** release for the tag, with the
   notes GitHub generates for the tagged commit (you can edit them: see
   "Editing the draft's release notes" below). `release_draft.py ensure`
   refuses a tag whose release is already published or that does not
   point at the commit the run builds, whether the draft is new or
   already exists, and waits until the release list shows a new draft
   (the list lags behind a fresh release by a moment). The job then
   stages `stream-to-speaker-<ver>.exe` as
   a workflow artifact, EV-signs it via the signing repo (**approval
   click 1**) and uploads the signed exe, its `.sha256` and its
   provenance bundle to the draft. The signed exe's SHA-256 is a job
   output; `package` and `publish` accept only that exe from the draft.
3. `package` — fetches the Microsoft-signed driver matching this tag's
   driver source (certified preferred over attested); an error while
   looking for it stops the job, and only "no driver release matches"
   leads to the fallback below. Stages it with the *signed* service exe
   from the draft (it must hash to what `sign-service` signed in this
   run; no test cert) and builds
   `StreamToSpeakerSetup-<ver>.exe`, which leaves the job only as the
   workflow artifact `unsigned-setup-exe` (name and SHA-256 are job
   outputs). The Microsoft-signed driver ships *inside* the installer and
   is deliberately not published as a standalone asset (see
   `LICENSE-BINARIES.md`); the `driver-v*` prerelease keeps the canonical
   copy. If no Microsoft-signed driver matches, it falls back to the
   test-signed driver + cert and names the installer
   `StreamToSpeakerSetup-<ver>-testsigned.exe` with a warning — run Flow A
   (or D), then re-tag, if you wanted a production release. Such a
   version is published as a pre-release (see "Test-signed fallback
   releases" below). Before falling back, `driver_release.py
   fallback-check` stops the job when a certified or attested driver was
   built from the tag's very `driver/` and `include/` trees: the source
   hash moved (runner image, `.gitattributes`), not the driver. Either
   installer gets `devcon.exe` only if it carries a valid Authenticode
   signature by Microsoft (`Assert-MicrosoftSigned.ps1`).
4. `verify-driver` — the release gate. Runs `driver-reproducibility.yml`
   as a reusable workflow for the `driver-v*` release `package` picked:
   rebuilds the driver from the tagged commit (its driver source hash must
   equal the manifest's) the way that release's manifest says it was
   built, compares it with the release's reference package (certified:
   the lab package; attested: the unsigned driver in the submission CAB)
   and the shipped `Signed.zip`, then unpacks the `unsigned-setup-exe`
   artifact (exact name and SHA-256 from `package`) and requires its
   driver files to be that `Signed.zip` byte for byte, with no test
   certificate. Read-only token, no secrets. Called this way every input
   except `commit` must be non-empty (an empty `commit` means the
   caller's commit), and it reports `verified` / `driver_tag` /
   `installer_sha256` only when every check passed. For a `-testsigned`
   fallback it is skipped (that driver is CI's own build of the tag's
   driver source, from `build` or its driver cache; there is no
   Microsoft-signed package to compare) and `package` / `sign-release`
   say so in a warning. See "Reproducibility check" below for what each
   rebuild repeats.
5. `sign-release` — runs only when the gate reported `verified` = `true`
   for exactly the driver release and installer SHA-256 `package`
   reported (or the gate was skipped for the fallback). EV-signs the
   `unsigned-setup-exe` artifact (**approval click 2**; the signing
   request carries the SHA-256, so only those bytes can be signed) and
   uploads to the draft the signed `StreamToSpeakerSetup-<ver>.exe`, its
   `.sha256` (canonical), its provenance bundle and the stable
   `StreamToSpeakerSetup.exe` alias + `.sha256` (not for a `-testsigned`
   fallback: the permanent link must never lead to an installer that needs
   testsigning mode; `release_draft.py upload` decides with the rule
   `publish` checks). Then it deletes setup exe assets an earlier attempt
   left on the draft under another name (`release_draft.py prune`: a
   `-testsigned` installer when this one bundles a Microsoft-signed
   driver or the other way round, with sidecars and bundles, and the
   alias when this one is `-testsigned`). The signed installer's SHA-256
   is a job output.
6. `publish` — `release_draft.py check`: the draft must hold exactly the
   assets of a complete release (both exes, every `.sha256` naming its
   file and hash, a `.sigstore.json` per exe whose in-toto subject is that
   file, the alias identical to the setup exe, nothing else, every upload
   finished), the service exe and the setup exe must be exactly the bytes
   `sign-service` and `sign-release` signed in this run (their SHA-256 job
   outputs), and every `.exe` on it must carry a valid Authenticode
   signature (`signtool verify /pa`). Then it publishes the draft — only
   if the draft still holds the very assets that were checked (same asset
   ids) and the tag still points at the commit the chain built
   (publishing a draft whose tag is gone would recreate the tag at the
   release's target commit). It becomes the latest release
   (`make_latest=true`) unless a published release that is not a
   pre-release has a version at least as high, for example when a hotfix
   of an older line or a chain that finished late is published after a
   newer version; then `make_latest=false` and a warning, so
   `releases/latest`, the stable download link and the update check stay
   on the newer version. `publish` runs one at a time across all tags, and
   when a higher version was published meanwhile, it gets latest back. A
   `-testsigned` fallback, and a version with a pre-release part
   (`v0.1.11-rc.1`), is published as a pre-release with
   `make_latest=false` (see below). `publish` runs after
   `sign-release` also in the test-signed fallback (explicit status
   checks: the skipped gate does not carry through). Until then no
   release and no release asset of the version is public. The tag is, and
   so is the run itself: as for any run in a public repository its logs
   and workflow artifacts can be seen and downloaded by signed-in GitHub
   users. A tag run therefore uploads no test-signed dev installer (the
   `build` job's `StreamToSpeakerSetup-<ver>` artifact, with its
   `.driver.json` record, exists only for dev and pull-request builds; on
   a tag run the bundled-driver record is in the step summary only), and
   every artifact it uploads with unsigned binaries in it —
   `binaries-<ver>` (the unsigned service exe and the test-signed
   driver), `release-inputs`, `unsigned-service-exe`, `unsigned-setup-exe`
   and the release gate's `driver-reproducibility-<driver tag>-unsigned-setup-exe`
   (the unsigned rebuilt driver, copies of the reference and shipped
   packages) — expires
   after one day, the minimum; the chain's jobs read them within the
   hours the run takes. The `cleanup` job runs after `sign-release`
   finishes or is skipped; it then deletes `unsigned-service-exe` if
   `sign-service` succeeded, and `unsigned-setup-exe`, `release-inputs`
   and `binaries-<ver>` if `sign-release` succeeded, since nothing reads
   them after that. Until then they stay downloadable. The gate's
   comparison artifact is not deleted; it expires.

Final release assets: signed `StreamToSpeakerSetup-<ver>.exe`, signed
`stream-to-speaker-<ver>.exe`, the `StreamToSpeakerSetup.exe` alias,
`.sha256` sidecars for each and `.sigstore.json` provenance bundles for
the two versioned exes.

Unsigned bytes travel to the signing repo as Actions artifacts fetched
with its `FETCH_TOKEN` (nothing depends on public release URLs). Uploads
to the draft go through `release_draft.py upload`, which first checks, as
`release_draft.py require` does, that the tag has exactly one release,
that it is a draft and that the tag still points at the run's commit (so
a run whose tag was moved since neither uploads nor asks for the
installer signature), and never deletes an asset before its replacement
is up. The chain checks that the version is the tag's (`vX.Y.Z` ↔
`X.Y.Z`), and the release jobs' scripts read the tag, version and hashes
from environment variables, never from expressions spliced into the
script text. If a job fails or is cancelled,
nothing is published; re-run the failed jobs and the chain continues on
the same draft. Re-running `package` builds a new installer (new SHA-256) and
re-runs `verify-driver` and `sign-release` after it, so that rebuild is
gated and signed in turn. The jobs pass their inputs as workflow
artifacts, which expire after one day: re-running a job (or approving a
signing request) more than a day after the artifact it reads was
uploaded fails before anything is signed — re-run all jobs instead,
which uploads every artifact again and asks for both approvals again.
The same holds once `cleanup` deleted an artifact: after `sign-release`
succeeded only `publish` can be re-run on its own. A
published release keeps its assets and notes (`publish` only hands the latest flag back to a higher version published meanwhile): once `publish` succeeded,
re-running the chain fails at `sign-service`.

### Editing the draft's release notes

You can edit the draft's notes until `publish` runs; they are published
as they stand. No run replaces notes you changed.

The notes `sign-service` generates end with a comment line that GitHub
hides when it shows the notes; you see it in the edit box. It names the
commit the notes were generated for and holds their SHA-256, which is how
a later run tells generated notes from changed ones. You can leave the
line where it is or delete it.

A run replaces a draft's notes in one case only: the tag was moved to
another commit after an earlier run made the draft, and the notes are
still exactly the generated ones. They are then generated again, for the
new commit. Notes you changed stay as they are in that case too, and the
run shows a warning that they were written for another commit: read them
again before the release is published. (The "Generate release notes"
button in the draft's edit box makes the list for the commit the tag
points at now.)

### Test-signed fallback releases

A version whose installer bundles the test-signed driver
(`StreamToSpeakerSetup-<ver>-testsigned.exe`, because no certified or
attested driver release matches the tag's driver source) is published as
a **pre-release** and never made the latest release. So is a version with
a pre-release part (`v0.1.11-rc.1`), whatever driver it bundles. `releases/latest`,
the stable `/releases/latest/download/StreamToSpeakerSetup.exe` link (the
release carries no alias anyway) and the app's update check, which reads
`releases/latest` and ignores pre-releases, all keep pointing at the last
release with a Microsoft-signed driver. The pre-release itself is public:
it is listed on the repository's releases page, marked as a pre-release,
with its installer as a download. That installer loads the driver only in
testsigning mode and imports the CI test certificate into the machine's
`Root` and `TrustedPublisher` stores (uninstalling removes it again).
Such a release is for testing that version on machines with testsigning
mode enabled, for example while the driver's signing round is still
running. To ship the version, finish Flow A or D for that driver source
and tag a new version.

### When the release gate fails

A failed `verify-driver` leaves only the draft (with the signed service
exe) and the tag; the installer is unsigned and was never published. The
failing step and the run summary tell a real mismatch from a broken
check:

- **Resolve parameters** — the gate was called with an empty or
  malformed input: `build.yml` was edited, not a driver problem.
- **Download the installer artifact** — the `unsigned-setup-exe`
  artifact is missing or expired (it is kept for one day): re-run all
  jobs, which builds and uploads it again.
- **Fetch release manifest and reference package** — the manifest is
  unusable (the field is named), the reference archive does not hash to
  what the manifest records (the release was altered: investigate), the
  driver source hash of the tag differs from the manifest's (the tag does
  not hold the tree that driver release was built from), or no build
  directory could be derived (attested: the submitted `.sys`'s PDB path
  has an unexpected form and the manifest records no `build_root`).
- **Fetch and verify the shipped driver package** — the `Signed.zip`
  does not hash to the manifest's `signed_zip_sha256` or does not hold
  exactly one `.sys`/`.inf`/`.cat`, its catalog or (attested) embedded
  `.sys` signature does not verify with the *Microsoft Windows Hardware
  Compatibility Publisher*, or (attested) its `.sys`/INF are not the
  submitted ones. The release was altered or is broken: investigate. A
  download error is transient: re-run.
- **WDK steps, `Build driver`** — a runner-image or toolchain problem
  (WDK download or install, MSBuild failing, or for an attested release
  "cannot create the build directory": the runner's checkout path no
  longer matches the path the driver was linked at). A broken check.
  "already exists on this runner": the build directory (`C:\build\src`
  for a certified release) was already there when the job went to create
  it. The check never deletes or reuses a directory it did not create;
  find out what put it there (a runner-image change) instead of working
  around it.
- **Verdict: "differs ... beyond the masked fields"** — read the summary.
  Differences together with a differing Rich header row (compiler,
  linker or library build ids) point to codegen drift in the runner
  image's toolset; a difference with the same toolset, or one in the
  shipped package only, is a real mismatch — stop and investigate.
  Differences confined to `.rdata` / debug-directory sizes mean the build
  directory's path length differs from the original build's.
- **Check the installer bundles the shipped package** — this step does
  not stop the job itself (so the summary and the artifact are still
  written); the job then fails at **Verdict** with "installer check
  (...) failed", and this step's log says why. "innounp-2.zip
  sha256 ..." or a download error: the pinned innounp release moved (a
  broken check; review and re-pin it). "innounp could not unpack": the
  Inno Setup version pinned in `build.yml` (`INNO_SETUP_VERSION`) writes a
  format the pinned innounp cannot read (a broken check; bump the two
  pins together).
  "does not bundle the shipped package" or "ships a test certificate":
  a real mismatch in what `package` staged.

The release chain runs the workflow files of the tagged commit, so a fix
to the check itself (or to the driver pairing) needs a new commit and a
new tag; re-running only helps with transient failures (network, runner).
To drop the version: `gh release delete vX.Y.Z --yes` deletes the draft
(add `--cleanup-tag` to delete the tag as well). A draft that is kept for
a later re-run may hold setup exe assets of the earlier attempt under
other names (for example a `-testsigned` installer when the next attempt
bundles a Microsoft-signed driver); `sign-release` removes those. A
draft an earlier run made for another commit (the tag was deleted and
pushed again elsewhere) is used again: its generated release notes are
generated again for the new commit, and notes you changed are kept (see
"Editing the draft's release notes"). Any
other asset that does not belong to a complete release makes `publish`
refuse the draft; remove it with
`gh release delete-asset vX.Y.Z <name> --yes`. A moved tag (deleted and
pushed again at another commit) leaves the draft to the run of the new
commit: runs of the old commit stop at their next `require`.

## Flow D — WHQL certification (HLK run by hand, the rest automated)

Used for driver **1.1.0.209** (product `14599256519720956`, submission
`1152921505701928485`, `WINDOWS_v100_X64_25H2_FULL`), release
`driver-v1.1.0.209`. Its
[certification report](https://partner.microsoft.com/en-us/dashboard/hardware/Driver/DownloadCertificationReport/95342530/14599256519720956/1152921505701928485)
(`95342530` in that URL is the seller ID, not a report ID).

1. **Lab.** Build the driver (`SignMode=TestSign` is fine — Microsoft
   replaces nothing but adds its own signatures), run the WHCP playlist
   on an HLK client, package the results in HLK Studio and sign the
   `.hlkx` with the EV cert. Keep the exact INF/SYS/CAT the client ran:
   it is the reference the workflow compares Microsoft's return against.
   The reproducibility check (below) rebuilds a certified release from
   the committed tree (`driver.h` not stamped) in `C:\build\src` with
   `/p:DriverBuildNumber=<build>`; a lab build made differently (stamped
   `driver.h`, another build number, a build directory whose path has
   another length) does not verify, and the release gate then stops the
   installer signature.
2. **Submit by hand** at Partner Center (Hardware → Submit new hardware →
   upload the `.hlkx`, tick the offered OS, no test-signing options). Note
   the product id and submission id from the URL.
3. **Prepare the release**: create `driver-v<ver>` (prerelease) targeting
   the commit whose `driver/**` + `include/**` tree is what the lab
   tested, and attach the lab package as
   `StreamToSpeaker-Driver-<ver>-lab-testsigned.zip`.
4. **Run `Driver certified`** (Actions → Run workflow) **from main** with
   `version`, `commit` (the full SHA of that commit; leave it empty when
   it is main's head), `product_id`, `submission_id`, `report_id` (the
   seller ID: the first number in the dashboard's certificationReport
   URL). Only main can use the `partner-center` environment that holds the
   Hardware API secrets; the run takes its scripts from main and hashes
   and records the `commit` tree, after checking that `commit` has the
   same `driver/` and `include/` trees as the commit the release's tag
   points to. `dry_run=true` runs every check below and leaves every
   release as it is (none is created, uploaded to or changed), with
   `ms_zip_asset` only: a dry run holds no credential, so it doesn't call
   the Hardware API. It polls the Hardware API until the submission is
   `completed` with a `signedPackage`, downloads it, and verifies:
   - INF byte-identical to the lab package and carrying DriverVer `<ver>`;
   - `.sys` code identical to the lab `.sys` after stripping the
     Authenticode certificate table (what `signtool remove /s` does) —
     Microsoft *adds* a nested signature, the lab test signature stays
     primary, so `driver-attested.yml`'s "primary signer must be
     Microsoft" check would reject a correct HLK return;
   - `signtool verify /kp /v /c` against the re-issued catalog (this is
     what the kernel relies on), and a *Microsoft Windows Hardware
     Compatibility Publisher* signature on the `.sys` at any index of
     `signtool verify /all`.
   Then it makes the canonical `…-Signed.zip`: Microsoft's INF, SYS and
   CAT and nothing else, in one fixed layout (no folder, fixed dates and
   attributes, host 0 in the zip's headers as in every Windows-made
   package). The job `publish` (main only, never in a dry run) attests the
   provenance of that very file and publishes it; it never makes one
   again. Before it writes anything it checks that the file has the
   SHA-256 `verify` reported for the package it made, that byte for byte
   it is that layout around exactly Microsoft's three files, and that the
   provenance bundle names it. With the `…-Signed.zip` it publishes
   `StreamToSpeaker-Driver-<ver>-Microsoft.zip`
   (as returned; the hand-attached lab package is checked, never uploaded
   again), the `.sha256` sidecars and the provenance
   bundle, and last `manifest.json` with
   `certified: true`, `certification: {product_id, submission_id, os,
   report_id}`, `source_hash` computed on the windows-2022 runner, and
   the fields the attestation manifests share with it (`attested: false`,
   `ms_state: done`, no submission CAB; the attestation-only `build_root`
   and `driver_h_stamped` are not written).
   Already have the zip from the dashboard? Attach it to the release and
   pass its name as `ms_zip_asset` — the API step is skipped and no Azure
   secrets are needed. Run it from main all the same: `publish` runs
   nowhere else; a dry run works from the branch of a change to this
   workflow.
5. Merge the driver branch. `Driver submission` fires on the `driver/**`
   push and its `certified-guard` stops it; `build.yml` bundles the
   certified package into every installer whose driver tree still hashes
   to the manifest's `source_hash`.

The script behind it is `.github/scripts/certified.py` (`inputs`, `hash`,
`fetch`, `verify`, `package`, `park`, `release`; `inputs` checks every
dispatch input and writes the values all later steps use; unit tests in
`test_certified.py`, run in the workflow's guard step). `release` can be
run locally with `gh` to publish a release from hand-downloaded files,
after `package` made the canonical zip: `release` takes that file as
`--signed-zip` and the SHA-256 that `package` printed for it
(`signed_zip_sha256=…`) as `--signed-zip-sha256`. The
same inputs again change nothing, and a release that is already
certified is never changed (other inputs are refused). Published
packages keep the bytes they were made with: `driver-v1.1.0.209`'s was
made on Linux (host 3 in its headers), `driver-v1.1.1.211`'s on Windows
(host 0, the layout `package` writes everywhere now). The layout is the
same wherever `package` runs; the compressed bytes inside it come from
that machine's zlib, and another zlib may compress the same files
differently. So a package is made once and handed on as a file, and
nothing rebuilds a published package: every check compares it with the
SHA-256 its manifest records.

## Reproducibility check (`driver-reproducibility.yml`)

Run from the Actions tab with a `driver-v*` `tag` to audit a release
(optionally `commit` = the commit to build when the branch head is not
that driver's source, and `installer_tag` = a published `v*` release
whose installer to unpack). Called from another workflow
(`workflow_call`) it is the `verify-driver` release gate: then `tag`,
`installer_artifact`, `installer_name` and `installer_sha256` are all
required and must be non-empty (`commit` may be empty: the caller's
commit), the installer is a workflow artifact of the same run, the
comparison artifact is kept for one day, and the outputs `verified` (`true` only when every check
passed), `driver_tag` and `installer_sha256` say what was verified. How
the release was built follows from its `manifest.json` (its kind, build
number and reference package, see the table); a manifest that is neither
`certified` nor `attested`, or lacks a field the rebuild needs, fails the
run with the field named.

| | Certified (`certified: true`) | Attested (`attested: true`) |
| --- | --- | --- |
| Reference binary | `.sys`/`.inf` in `lab_zip` (test-signed lab package) | unsigned `.sys`/`.inf` in `submission_cab` (the EV-signed CAB on the release, SHA-256 = `submission_cab_signed_sha256`) |
| `driver.h` build constant | as committed | stamped with `driver_build`, as `Driver submission` does |
| Build directory | `C:\build\src` | where the submitted `.sys` was linked: from its PDB path, or the manifest's `build_root` when that path has an unexpected form (a `build_root` that disagrees with the binary only warns) - normally the runner checkout, then built in place |
| Build tree vs checkout | byte-identical | identical except the stamped constant |
| Shipped `Signed.zip` | catalog verifies (Microsoft); `.sys`/`.inf` match the rebuild | the same, plus: embedded `.sys` signature verifies (Microsoft is the primary signer), `.sys` equals the submitted one with signatures stripped, INF byte-identical to the submitted one |

Both use msbuild `Release|x64`, `SignMode=Off`,
`DriverBuildNumber=<driver_build>`, require the checkout's driver source
hash to equal `source_hash`, and compare `.sys` files with signatures
stripped and only build-varying header fields masked: the COFF
timestamp, the PE checksum, the debug-directory timestamps and the
CodeView (PDB GUID, age, path) and REPRO debug payloads; the header block
is compared from each file's own offset. The INF is compared with the
DriverVer date masked. The linker embeds the PDB path and its length
shifts the image layout, so the rebuild has to happen at the same path;
the path text itself is among the masked fields.
Compiler/linker build ids (Rich header) are reported and only warn. The
installer's driver files (`installer_tag` or the gate's artifact) must be
the `Signed.zip` contents byte for byte and carry no test certificate.

Release files are downloaded and unpacked under the runner's temp
directory, outside the checkout, and archive members are picked by file
name and written flat (never to a path taken from the archive). The
checkout's driver source hash is checked against the manifest before any
release archive is fetched, and again as the build step starts. Text from release files reaches the log
only cleaned (`repro_compare.py` `clean_text`) or between
`::stop-commands::` markers, so it cannot act as a workflow command.

## What is and isn't signed

| Artifact | Signature | Why |
| --- | --- | --- |
| `StreamToSpeaker.sys` / `.cat` (release) | Microsoft (WHQL certification; attestation as fallback) | Only signature Windows accepts for kernel code |
| Submission CAB | Certum EV | Partner Center requirement |
| `stream-to-speaker.exe` | Certum EV | AV/firewall-prompt trust for the binary that actually runs |
| `StreamToSpeakerSetup-<ver>.exe` | Certum EV | SmartScreen reputation on the download |
| Inno uninstaller | unsigned | Inno signs it at compile time via a SignTool shim; wiring that through an approval-gated remote signer means another blocking approval inside ISCC — deferred |
| devcon.exe | Microsoft (from the WDK, through the driver cache) | `build.yml` checks its Authenticode signature before every installer build; nothing here builds it |
| Dev/PR artifacts, test-signed driver | self-signed test cert | unchanged dev flow |

## Troubleshooting

- **`sign-cab` fails with an environment/branch error** — `main` isn't in
  the `request-signing` environment's deployment-branch policy (one-time
  setup, above).
- **Partner Center rejects the CAB** — check the architecture selections
  match the INF (we only have `NTamd64` sections: select only x64 targets);
  "EV certificate is not valid" means the cert isn't associated with the
  Partner Center account.
- **`Driver attested` fails INF comparison** — the zip doesn't belong to
  that submission (version mixup) or was repacked; re-download from Partner
  Center and attach as-is.
- **Release says `-testsigned` (and is a pre-release) unexpectedly** — the driver source changed
  after the last signing round (any edit under `driver/` or `include/`
  changes the hash — a comment counts). The `package` job's warning names
  the newest certified/attested `driver-v*` release and the `source_hash`
  it records next to the tag's; or run
  `python3 .github/scripts/certified.py hash` locally. When the job
  stopped instead with "was built from the same driver/ and include/
  trees", the driver did not change but the hash came out different (a
  runner image or `.gitattributes` change alters `hashFiles()`): find what
  changed the hash before tagging again.
- **`Driver submission` stops with "would number this driver below …"**
  — see "Driver build numbers": dispatch it from main with `driver_build`
  above every existing release's build number.
- **`Driver submission` stops with "… is a certified driver release; a
  finished driver release is never changed"** (or "holds the driver of
  commit …", "already holds the EV-signed CAB") — the tag this run
  computed belongs to another release. Nothing was built or written;
  dispatch with another `driver_build`.
- **A release shows an asset named `<name>.pending`** — a run stopped while
  it replaced `<name>` (or, rarely, a write from outside the writers'
  group met one of them; see "How the chain writes driver releases"). Open
  the run that stopped and choose "Re-run failed jobs": the job that was
  writing the release (`record` or `record-signed` of Driver submission,
  `reconcile` of Driver attest, `record` of Driver attested, `publish` of
  Driver certified) first finishes its own write, then goes on. Run
  again, that job
  - puts `manifest.json.pending` in place when it is, byte for byte, the
    manifest it writes next, after the files and the release notes it
    writes before its manifest;
  - deletes a pending copy of a file it uploads (the EV-signed CAB,
    Microsoft's zip, the canonical `…-Signed.zip`, a `.sha256` file, a
    provenance bundle) and uploads the file itself;
  - puts a pending copy of a file the manifest records in place only in
    exactly the recorded bytes.

  No other job finishes the write. Any job that meets a pending file
  that is not its own stopped write stops with "holds a .pending file
  that this job does not finish: …; nothing was changed", naming the file
  and what is wrong with it. That includes the same job with other
  inputs: a new Driver attested run, or "Re-run all jobs" on the one that
  stopped, makes the canonical zip again, and when its bytes differ from
  the stopped attempt's, the pending manifest is not the one the new
  attempt writes. Driver attest is the exception: its save depends on
  nothing but the release, so any later Driver attest run for the tag
  finishes it.

  Until a pending manifest without `manifest.json` is finished, the
  installers' driver lookup, the certified guard and the fallback check
  stop at that release, so every tag's `package` job and every Driver
  submission run stop too. When the job that stopped can't be run again
  (its run is older than GitHub's 30-day re-run limit, or an artifact it
  needs has expired), see "Clearing a `.pending` asset by hand" below.
- **A job says "… changed since this run last read it … another run or a
  person is writing it"** — the release changed between the job's read
  and its write (a file attached by hand, or a run from outside the
  writers' group). Nothing more was written. Look at the release, then
  re-run the job.
- **`devcon.exe` "carries no valid Authenticode signature" or "is not
  signed by Microsoft"** — `Assert-MicrosoftSigned.ps1` stopped the
  installer build: the devcon.exe in the WDK (or in the driver cache built
  from it) is not the Microsoft-signed one. Look at the signer and SHA-256
  it printed. If the cached copy is the odd one out (the runner image's
  WDK changed since), bump the `vN` tag of the driver cache key in
  `build.yml` so the cache is built again from the current WDK; if the
  WDK's own devcon.exe is signed differently, the check's expectation
  needs a look before anything is released.
- **Installer bundles an attested build although a certified one exists** —
  their `source_hash` differs: the certified manifest pairs only with the
  exact tree the lab tested. Either restore that tree or run a new HLK
  round.
- **`Driver certified` fails the signtool step on index 0** — expected
  noise: the primary signature is the lab test cert (untrusted on the
  runner); the step only requires the Microsoft signature at some index
  plus a passing catalog verification. If the catalog check fails, the
  zip is not the return for that lab package.
- **`Driver submission` skipped everything** — its `certified-guard` found
  a certified release for the current source hash (by design); dispatch
  with `force=true` if you really want an attestation build too.
- **`Driver attest` did nothing after `Driver submission`** — automatic
  attestation is opt-in (`AUTO_ATTEST` repository variable); run it
  from main with the release's `tag`.
- **Signing run never appeared / wrong digest** — the composite action
  polls 5 min for a new run whose title contains the digest, then waits
  for approval. A re-run of a signing job follows a run for the same
  digest that still waits, and reuses the signed file of one that
  succeeded; see `.github/actions/request-signing/SigningRun.ps1`.
- **`Driver attest` fails at the token step (`invalid_client`)** — the
  Entra client secret expired or was rotated without updating the
  `partner-center` environment's `AZURE_CLIENT_SECRET` (see one-time
  setup, step 4).
- **`Driver attest` or `Driver certified` is refused with "not allowed to
  deploy to partner-center"** — the run was dispatched from a ref other
  than main. Dispatch it from main (for `Driver certified`, with
  `commit` = the certified commit), or use a dry run (for `Driver
  certified` with `ms_zip_asset`), which needs no environment.
- **`Driver attest` fails creating the product/submission** — the Entra
  app lost its Partner Center association or Manager role (Account
  settings → User management → Microsoft Entra applications).

### Clearing a `.pending` asset by hand

Do this only when the job that left the file can't finish it (see "A
release shows an asset named `<name>.pending`" above): GitHub no longer
re-runs its run (after 30 days), the re-run fails before it reaches the
release because an artifact it needs has expired (the EV-signed CAB is
kept 3 days, the canonical packages 7), or no run of these workflows
left the file. A job finishes only what it can show to be its own
stopped write. By hand you make its checks yourself, so that the release
ends up as a run would have left it.

Work in a clone of this repository, with `gh` signed in to an account
that can write to it, while no run of Driver submission, Driver attest,
Driver attested or Driver certified is running or waiting. In the
commands, `driver-v<ver>` is the release's tag; `{owner}` and `{repo}`
stay as they are (`gh` fills them in from the clone).

**1. List what the release holds.**

```sh
gh api "repos/{owner}/{repo}/releases/tags/driver-v<ver>" --jq '.assets[] | [.id, .state, .size, .name] | @tsv'
```

Each line is one asset: its id, its state, its size in bytes and its
name. The state is `uploaded` once an upload completed; an asset in any
other state holds nothing.

**2. Deal with every name that ends in `.pending`**, with
`manifest.json.pending` last. Three commands do all of it:

```sh
gh release download driver-v<ver> --pattern '<name>' --output <file>
gh release delete-asset driver-v<ver> '<name>' --yes
gh api --method PATCH "repos/{owner}/{repo}/releases/assets/<id>" -f name=<new name>
```

The first fetches an asset so that you can look at it, the second deletes
one, the third gives the asset with that id a new name.

- **The release is finished** (its `manifest.json` says `certified: true`
  or `attested: true`). Delete every `.pending` asset and change nothing
  else. No job renames anything on a finished release.
- **The state of `<name>.pending` is not `uploaded`.** The upload never
  completed and the asset holds nothing. Delete it.
- **`<name>.pending` and `<name>` are both there**, and `<name>` is not
  `manifest.json`. The release still holds the file as it was. Delete
  `<name>.pending`; the job that uploads `<name>` uploads it again when
  it next runs.
- **`<name>.pending` is there and `<name>` is missing**, and `<name>` is
  not `manifest.json`. See whether the release's manifest
  (`manifest.json`, or `manifest.json.pending` when that is all there is)
  records `<name>`. It does when `<name>` is its `signed_zip`, `lab_zip`
  or `ms_zip_asset`, or its `submission_cab` once
  `submission_cab_signed_sha256` has a value.
  - Not recorded (a `.sha256` file, a provenance bundle, the CAB while
    `submission_cab_signed_sha256` is still `null`): delete
    `<name>.pending`; the job uploads the file again when it next runs.
  - Recorded: the pending copy has to be that very file. The manifest
    gives the file's SHA-256 (`signed_zip_sha256`, `lab_zip_sha256`,
    `ms_zip_sha256`, `submission_cab_signed_sha256`). Download
    `<name>.pending` and compare its SHA-256 (`sha256sum <file>`; on
    macOS `shasum -a 256 <file>`). The same: rename `<name>.pending` to
    `<name>`. Not the same, or the manifest has no SHA-256 for it: stop.
    No run of these workflows leaves a release like that, so find out
    what changed it before you go on.
- **`manifest.json.pending`.** Fetch it, and `manifest.json` when the
  release has one, and compare the two:

  ```sh
  gh release download driver-v<ver> --pattern manifest.json.pending --output pending.json
  gh release download driver-v<ver> --pattern manifest.json --output current.json
  diff current.json pending.json
  ```

  **`manifest.json` is there.** The release still has its last complete
  manifest. What to do depends on the lines `diff` shows:
  - Only `ms_product_id`, `ms_submission_id`, `ms_state` or
    `ms_zip_asset`: a save of Driver attest. Don't delete it: it can hold
    the only record of the ids Partner Center gave this submission.
    Start Driver attest from main with this release as `tag`: any run of
    it finishes a save of its own. If that run stops at the pending
    manifest as well, Driver attest did not make this save on this
    manifest: stop, and find out what changed the release.
  - Only `submission_cab_signed_sha256`: the stopped job had the CAB
    EV-signed and was recording that. Download the asset the manifest
    names as `submission_cab` and compare its SHA-256 with the new value.
    The same: delete `manifest.json`, then rename `manifest.json.pending`
    to `manifest.json`, and the signature is kept. Not the same: delete
    `manifest.json.pending`.
  - Anything else: delete `manifest.json.pending`. The release is as it
    was before the stopped job's last write. Start that job's workflow
    again from main, and it writes its manifest anew. This holds for a
    pending manifest that says `attested: true` as well: leave finishing
    a release to a run, which checks what it finishes.

  **`manifest.json` is gone.** The release has no manifest, and installer
  builds and Driver submission stop at it until it has one again.
  - If the pending manifest has an `ms_state` and says
    `attested: false`, start Driver attest from main with this release
    as `tag` first: a run of it finishes a save of its own, also without
    `manifest.json`. Go on here only when that run stops at the pending
    manifest as well.
  - Put back the manifest the release had before the stopped write. The
    run that wrote it (the last one that wrote this release before the
    one that stopped) shows it in its summary, under "manifest.json
    written to `driver-v<ver>`". Save that text as a file named
    `manifest.json`, check that it is whole
    (`python3 -m json.tool manifest.json` prints it), then:

    ```sh
    gh release upload driver-v<ver> manifest.json
    gh release delete-asset driver-v<ver> manifest.json.pending --yes
    ```

    The release is as it was before the stopped write. Start the stopped
    job's workflow again from main, and it makes its write anew, with
    its own checks.
  - If no run shows the earlier manifest, the pending one is the only
    record there is. Rename `manifest.json.pending` to `manifest.json`
    when all of these hold; when one doesn't, stop, and find out what
    changed the release:
    1. `python3 -m json.tool pending.json` prints it (it is whole).
    2. Its `driver_version` is the version in the tag, and its `commit`
       is the commit the tag points at
       (`gh api "repos/{owner}/{repo}/commits/driver-v<ver>" --jq .sha`).
    3. Every file it records (as described above) is on the release with
       state `uploaded`, and has the SHA-256 the manifest gives for it
       where it gives one.

**3. Check the result.** Run the command of step 1 again. No name ends in
`.pending`, and `manifest.json` is there with state `uploaded`. Then go
on with the flow from where the release stands, starting each workflow
from main. The job that stopped at the pending file before now reads the
release's manifest and goes on from it.

## Manual fallback (Partner Center in the browser)

If the Hardware API path is ever unavailable, the pre-automation flow still
works end to end:

1. Download the EV-signed `StreamToSpeaker-Driver-<ver>-Submission.cab`
   from the `driver-v<ver>` release.
2. Submit it at the [Partner Center hardware dashboard]
   (https://partner.microsoft.com/dashboard/hardware): *Submit new
   hardware* → upload CAB → leave both test-signing options unchecked →
   select the Windows 10 1809+ / Windows 11 **x64** targets → Submit.
3. Download the signed zip Microsoft returns and attach it to the same
   `driver-v<ver>` release (a `.zip` name of letters, digits and
   `. _ + -`; don't rename anything inside).
4. Run the **Driver attested** workflow from main (Actions tab; it picks
   the newest unfinished release with a zip attached, by creation date,
   or pass the tag). Same verification as the automatic path. Not while
   `Driver attest` runs for the same release (see Flow A's notes).

## Dry runs

A dry run executes only jobs that hold a read-only token and no secret:
the jobs that write (Driver attested's `record`, Driver certified's
`publish`, Driver attest's `reconcile`) are skipped, and no dry-run job
waits in the writers' group. `Driver attest` and `Driver attested` take a
`dry_run` input on manual dispatch. `Driver attested` with `dry_run=true` runs the signtool and INF
checks against the given `tag` (which may already be attested, e.g.
`driver-v1.1.0.204`) and stops before the release is modified. `Driver
attest` with `dry_run=true` skips the Hardware API entirely and calls
`Driver attested` in dry-run mode for `tag` (default
`driver-v1.1.0.204`), which exercises the reusable-workflow call — the
calling job must grant `contents: write`, `id-token: write` and
`attestations: write`, the permissions `driver-attested.yml`'s `record`
declares; the job a dry run executes there, `verify`, declares
`contents: read` and gets no more.
`Driver submission` needs no dry-run input: dispatched from a branch other
than main it builds the CAB (the `submission-cab` artifact) with a
read-only token and writes no release, and while a certified driver
matches the current source hash its `certified-guard` job ends the run
before anything is built. When it finishes, GitHub starts main's `Driver
attest`, which ignores a run that wasn't on main. `Driver certified` with
`dry_run=true` runs every check and changes no release; it needs
`ms_zip_asset` (the Hardware API path holds the Partner Center secret and
is refused in a dry run).
